# Contributing

Thank you for considering it. This paper applies to every repository in the organisation that does not carry its own. Where a repository has its own guide, that guide wins.

## Before you write anything

- **Look for an existing issue.** If there is one, add to it.
- **For anything larger than a small fix, open an issue first.** A proposal that is discussed before it is built is rarely wasted. One that arrives finished and unannounced often is.
- **A weakness is not an issue.** Report it privately, as [the security policy](SECURITY.md) describes.

## Making the change

- Keep it to one thing. Two changes are two pull requests.
- Follow the conventions already in the repository, including the ones you would have chosen differently.
- If the repository has tests, run them, and add one for what you changed.
- Write the commit message for the person who reads the history in a year: what changed, and why.

## If software helped

Say so. A change drafted in whole or in part by an AI system carries a trailer naming it:

```
Assisted-by: <the system>
```

You remain the author. You have read every line, you understand it, and you answer for it.

## What you are agreeing to

Your contribution is offered under the licence of the repository you are contributing to. Offer only work that is yours to offer.

## What happens next

A person reads every pull request. We do not promise how soon. A change may be declined for reasons that have nothing to do with its quality, and when that happens we will say why.
